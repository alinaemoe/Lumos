# Lumos — Technical Design Document

*Personal Computer Memory System*

---

## 1. Vision

Lumos превращает компьютер из набора разрозненных файлов в систему, которая понимает контекст работы пользователя. Не "умный поиск файлов" и не "чат с ИИ" — это локальный слой памяти между человеком и компьютером, который отвечает не на вопрос "где файл X", а на вопрос "что я делала, когда решала задачу Y".

Философия: **компьютер должен помнить так же, как помнит человек — через контекст, а не через имена файлов.**

---

## 2. Problem

Современная файловая система хранит метаданные (путь, имя, дата изменения), но не хранит намерение и контекст. Человек, работающий с 10+ репозиториями, десятками вкладок браузера, несколькими окнами VS Code, Docker/Kubernetes-окружениями и разными версиями инструментов (VS 2019/2022, macOS/Windows), физически не может держать в голове, "где я это делала" — и тратит время на:

- переключение между окнами в поисках нужной вкладки/файла;
- повторный поиск ссылок на ресурсы (доступы к Mongo/Stripe/Namecheap), разбросанных по письмам и документам;
- потерю кусков буфера обмена, когда нужно скопировать несколько вещей подряд (токены, скриншоты), а помещается только последняя;
- невозможность найти скриншот ошибки/интерфейса неделю спустя, если не помнишь точных слов, которые там были.

Существующие инструменты не закрывают это:

| Инструмент | Чего не хватает |
|---|---|
| Windows Search / Everything | Индексируют файлы, не поведение и не контекст |
| PowerToys | Набор утилит, не память |
| Raycast / Alfred | Launcher + расширения, нет долгосрочного контекста |
| Notion / Obsidian | Требуют ручного ввода, не пассивны |
| Microsoft Recall / Rewind.ai | Скриншот-центричны, часто без ручной таксономии проектов, вопросы к приватности |

---

## 3. Solution

Lumos пассивно наблюдает за файловой системой, буфером обмена и скриншотами, строит граф связей между этими объектами через понятие **сессии** (временной кластер активности, привязанный к проекту), и даёт единый Ctrl+Ctrl поиск, который понимает и точные совпадения (FTS5), и смысл (embeddings), и визуальное содержимое скриншотов (CLIP).

Ключевой архитектурный принцип: **вся система работает и без LLM.** Группировка в сессии, классификация типов данных, поиск по смыслу — всё это детерминированные правила и embedding-модели. LLM — опциональный слой перевода запроса на естественном языке в структурированный фильтр, включается только по явному запросу пользователя.

## 4. Features

### В MVP (v0.1–v0.3)
- Индексация файлов с ручной привязкой папок/git-репозиториев к именованным проектам ("CCM", "основной бек", "российская мобилка")
- Полнотекстовый (FTS5) + семантический (embeddings) поиск по файлам
- История буфера обмена (текст и изображения) с классификацией типа (JSON/SQL/JWT/GUID/stacktrace) и поиском по смыслу, а не по позиции в истории
- Screenshot pipeline: OCR (текстовое содержимое) + CLIP (визуальное содержимое — "скрин с синей кнопкой")
- Session Tracker: таймлайн активности без LLM (активное окно + время + проект)
- Ctrl+Ctrl overlay UI

### После MVP (v0.4–v1.0)
- AI Interpreter: LLM переводит запрос на естественном языке в структурированный фильтр
- Gmail-интеграция: поиск писем с доступами/инвайтами (Mongo, Stripe, Namecheap и т.д.)
- Архитектурная готовность к синхронизации между машинами (без реализации в v1)

### Явно вне скоупа (Non-Goals)
- Публичный продукт для чужих пользователей — это личный инструмент
- Постоянно висящая в фоне LLM-разметка событий — заменена детерминированными эвристиками
- Browser Intelligence (история браузера как отдельный отслеживаемый объект) — не обсуждалось предметно в интервью, откладывается на этап после Gmail, по той же полиморфной модели `session_events`
- Мобильный клиент
- Общая LLM-генерация SQL "на лету" — риск некорректных/небезопасных запросов; LLM только заполняет заранее заданную JSON-схему фильтра

## 5. Architecture

```
Lumos
├── Core Engine (orchestrator, Rust)
├── File Watcher
├── Indexer
├── Metadata Analyzer (project tagging)
├── Clipboard Monitor
├── OCR Pipeline
├── Embedding Pipeline (text + CLIP)
├── Search Engine (FTS5 + vector, hybrid ranking)
├── Session Tracker
├── AI Interpreter (on-demand, Ollama)
└── UI (Tauri overlay)
```

| Модуль | Назначение | Технологии | Данные | API |
|---|---|---|---|---|
| Core Engine | Оркестрация модулей, владение SQLite-соединением | Rust, tokio | — | Внутренние каналы |
| File Watcher | Ловит create/modify/delete/rename в реальном времени | `windows-rs` (USN Journal + ReadDirectoryChangesW) | Сырые события (не хранятся) | Внутренний |
| Indexer | Хэш, размер, extension, связь с проектом | Rust, rusqlite | `files` | Внутренний |
| Metadata Analyzer | Ручная привязка папка→проект + автоопределение типа репо по маркерным файлам | Rust, правила | `projects`, `project_paths` | UI-форма привязки |
| Clipboard Monitor | Перехват текста/изображений, regex-классификация типа | `windows-rs` (WM_CLIPBOARDUPDATE) | `clipboard_entries` | Внутренний |
| OCR Pipeline | Извлечение текста из скриншотов | Windows.Media.Ocr | `screenshots.ocr_text` | Внутренний, асинхронная очередь |
| Embedding Pipeline | Текстовые (BGE/E5) и визуальные (CLIP) векторы | ONNX Runtime (`ort`) | `sqlite-vec` таблицы | Внутренний, низкий приоритет потока |
| Search Engine | Гибридный поиск: FTS5 + vector, RRF ranking | SQLite FTS5 + sqlite-vec | Читает из всех таблиц | `search(query) -> results` — единственная внешняя точка для UI |
| Session Tracker | Группировка событий в сессии по времени/окну/проекту | Rust, эвристики, `GetForegroundWindow` | `sessions`, `session_events` | Внутренний |
| AI Interpreter | Query parsing на естественном языке → JSON-фильтр | Ollama (HTTP, localhost) | Stateless | HTTP к локальному Ollama |
| UI | Ctrl+Ctrl overlay, поиск, превью результатов | Tauri (Rust + WebView) | — | Tauri IPC → Core Engine |

## 6. Tech Stack

| Слой | Выбор | Обоснование |
|---|---|---|
| Core/Backend | **Rust** | Долгоживущий фоновый процесс — memory safety снимает целый класс багов; `windows-rs` даёт прямой доступ к USN Journal/ReadDirectoryChangesW; `tokio` — параллельные пайплайны без блокировок; cargo проще поддерживать соло на дистанции месяцев, чем CMake/vcpkg |
| Desktop UI | **Tauri** | Rust-бэкенд + системный WebView вместо Chromium (в отличие от Electron) — меньше памяти, быстрый старт overlay-окна, прямой IPC без сетевого слоя |
| Database | **SQLite + FTS5** | Локально, ноль конфигурации, справляется с миллионами записей, зрелый Rust-биндинг (`rusqlite`) |
| Vector search | **sqlite-vec** | Хранит embeddings в той же SQLite-базе — без отдельного сервера (Qdrant/FAISS), вся система остаётся одним локальным файлом |
| OCR | **Windows.Media.Ocr** | Встроен в ОС, без скачивания моделей; запасной вариант — Tesseract, если качество не устроит на мелком шрифте/коде |
| Text embeddings | **BGE-small / E5-small (ONNX)** | Лёгкие модели (100–400MB), быстрый CPU-инференс через `ort` |
| Visual embeddings | **OpenCLIP ViT-B/32 (ONNX)** | Тот же `ort`-рантайм, что и текстовые embeddings — не нужна вторая инференс-инфраструктура |
| LLM | **Ollama + Qwen3 4B / Gemma3 4B** | Отдельный локальный HTTP-процесс, не встроен в Rust-ядро; CPU-инференс приемлем для on-demand запроса (не для потокового фона) |

**Почему не GPU-инференс:** встроенная Radeon 780M не имеет dedicated VRAM — всё держится на CPU (Ryzen 7 8845HS, 8c/16t, 32GB DDR5 — достаточно для фоновой индексации + embeddings + on-demand LLM одновременно с обычной разработческой нагрузкой).

## 7. Database

Полная DDL-схема — см. раздел 8 обсуждения (таблицы `projects`, `project_paths`, `files`, `clipboard_entries`, `screenshots`, `sessions`, `session_events`, плюс `sqlite-vec` virtual tables `file_text_embeddings`, `clipboard_text_embeddings`, `screenshot_text_embeddings`, `screenshot_visual_embeddings`).

Ключевой архитектурный приём: `session_events` связывает сессию с любым типом объекта полиморфно через `(event_type, ref_id)` — это позволяет добавлять новые типы объектов (browser_history, Gmail-письма) без миграции таблицы `sessions`.

```
projects 1───* project_paths
projects 1───* files
projects 1───* clipboard_entries
projects 1───* screenshots
projects 1───* sessions

files ──1:1── file_text_embeddings (по rowid)
clipboard_entries ──1:1── clipboard_text_embeddings
screenshots ──1:1── screenshot_text_embeddings
screenshots ──1:1── screenshot_visual_embeddings

sessions 1───* session_events *───1 (files | clipboard_entries | screenshots)  — полиморфно
```

*(Полный SQL DDL — отдельный файл `schema.sql`, зафиксирован в переписке от этапа проектирования БД.)*

## 8. AI Pipeline

**Где LLM нужна:** единственная точка — AI Interpreter. Переводит запрос на естественном языке в структурированный JSON-фильтр (тип объекта, временной диапазон, project_id, action). LLM никогда не генерирует SQL напрямую — только заполняет заранее заданную схему, что убирает риск некорректных/небезопасных запросов.

**Где LLM не нужна:**
- Session Tracker — детерминированные эвристики (время + активное окно + проект), иначе группировка сессий станет непредсказуемой
- Clipboard classification — regex/паттерны быстрее и надёжнее LLM на каждую копию
- Project/repo type detection — по маркерным файлам (package.json, .csproj, Dockerfile)

**Остальные модели:**
- OCR — извлечение текста, не "понимание", результат идёт в обычный текстовый пайплайн
- Text embeddings (BGE/E5) — семантическая близость через векторы, без генерации
- CLIP — раздельные энкодеры изображения/текста в общее векторное пространство, поиск — nearest-neighbor

**Работа без LLM (graceful degradation):** все модули, кроме AI Interpreter, работают полностью независимо от Ollama. Если Ollama не запущен или недоступен — Search Engine молча использует сырой текстовый запрос напрямую в FTS5+vector search, без ошибок и без блокировки функциональности. LLM — usability-бустер поверх уже рабочей системы, не критическая зависимость.

## 9. Security

*(Раздел добавлен как критически важный для системы, которая пассивно хранит буфер обмена и скриншоты — там неизбежно будут попадать токены, пароли, приватные данные.)*

- **Локальность по умолчанию:** вся БД (SQLite-файл) хранится локально, ничего не уходит в облако ни на одном этапе MVP. Ollama работает на localhost, без внешних API-вызовов.
- **Чувствительные данные в буфере — сознательное решение хранить всё.** Clipboard-классификатор определяет JWT/токены/GUID, но это используется только для типизации/поиска ("покажи тот токен, что копировала 10 минут назад"), а не для исключения из индекса — единственный пользователь системы и есть её владелец, экономия на полноте истории здесь не оправдана.
- **Шифрование at rest — основная мера защиты вместо exclusion.** Раз секреты (токены из clipboard, credentials из скриншотов) хранятся полностью, риск смещается в сторону "что если ноутбук/диск попадёт не в те руки" — закрывается через SQLCipher (шифрованная SQLite) вместо урезания сохраняемого контента. Это даёт и полную историю, и защиту при физическом доступе к устройству.
- **Исключение путей:** watcher не должен индексировать системные/приватные директории по умолчанию (`.ssh`, `.aws`, менеджеры паролей) — allowlist подход (индексировать только явно привязанные к проектам папки), а не blacklist.
- **Gmail-интеграция (v0.4+):** OAuth с минимально необходимым read-only scope, токены доступа хранятся в Windows Credential Manager, а не в самой SQLite-базе. Отдельный security review перед реализацией — это первая точка, где данные потенциально покидают чисто локальный контур (запрос к Google API).
- **Retention policy:** стоит заранее решить, есть ли TTL для скриншотов/clipboard (например, автоочистка старше N месяцев), чтобы база не превращалась в бессрочный архив потенциально чувствительных данных.

## 10. MVP

**Скоуп v0.1–v0.3** (без LLM, без Gmail, без синхронизации):

1. File Watcher + Indexer + FTS5-поиск по файлам
2. Ручная привязка папок/репозиториев к именованным проектам
3. Clipboard history (текст + изображения) с классификацией типа и embedding-поиском по смыслу
4. Screenshot pipeline: OCR + CLIP, поиск и по тексту, и по визуальному содержимому
5. Session Tracker: таймлайн активности без LLM
6. Ctrl+Ctrl overlay UI

**Критерий готовности MVP:** неделя реального использования, после которой поиск "тот скрин из монги вчера вечером" или "тот json перед созвоном" (даже без LLM-парсинга, просто через сырой embedding-запрос) находит нужный результат в топ-3 без ручного перебора.

## 11. Roadmap

### v0.1 — Файлы и базовый поиск (недели 1–4)
- Неделя 1: Rust workspace, `rusqlite`, схема `files`/`projects`, CLI для ручного скана
- Неделя 2: File Watcher (ReadDirectoryChangesW), обработка событий
- Неделя 3: Indexer — хэш/размер/extension, FTS5-индекс по filename
- Неделя 4: Metadata Analyzer — ручной конфиг проектов, автоопределение типа репо

### v0.2 — UI и Clipboard (недели 5–8)
- Неделя 5: Tauri overlay, глобальный хоткей Ctrl+Ctrl, базовый FTS5-поиск в UI
- Неделя 6: Clipboard Monitor — перехват + regex-классификация
- Неделя 7: Text embeddings (BGE/E5) через ONNX Runtime, `sqlite-vec`
- Неделя 8: Гибридный Search Engine (FTS5 + vector, RRF ranking)

### v0.3 — Скриншоты и сессии (недели 9–14)
- Недели 9–10: Захват скриншотов, OCR pipeline, текстовый embedding по OCR
- Недели 11–12: CLIP pipeline (ViT-B/32 ONNX), визуальный поиск
- Неделя 13: Session Tracker — active window tracking, эвристики группировки
- Неделя 14: UI-доработка (таймлайн сессии), неделя реального использования вживую

### v0.4–v1.0 — LLM и Gmail (без фиксированных сроков)
- AI Interpreter: Ollama, structured query parsing
- Gmail-интеграция: OAuth, парсинг писем с доступами, отдельный security review
- Retention policy и опция шифрования (SQLCipher), если к этому моменту актуально
- Архитектурная подготовка к синхронизации (не реализация)

## 12. Future Ideas

- Browser Intelligence (вкладки, история, downloads) — тем же полиморфным паттерном `session_events`
- Синхронизация между машинами (макбук + десктоп) — после того как MVP доказал ценность на одной машине
- Фоновая LLM-разметка событий как опциональный режим (сейчас сознательно исключена в пользу предсказуемости)
- Плагины/расширяемость под новые типы объектов (по аналогии с Gmail/Browser)
- Экспорт сессии в человеко-читаемый отчёт ("что я делала над CCM за последнюю неделю")

## Open Risks

- **Session Tracker — самая рискованная часть.** Эвристики могут давать ложные разбиения (слишком много мелких сессий или наоборот слипание разных задач) — потребуется итеративная настройка порогов на реальном использовании, а не единоразовая калибровка.
- **Gmail-интеграция** — самый большой риск по скоупу и приватности среди всех запланированных функций; сознательно отложена до подтверждения ценности core-функциональности.
- **Хранение секретов в clipboard/screenshots** — решено хранить всё без исключений (сознательный выбор для личного локального инструмента), риск компенсируется шифрованием БД (SQLCipher), а не урезанием контента. Важно внедрить шифрование на старте, а не мигрировать уже наполненную базу позже.
