## Phase 1 — Общий обзор: архитектурные ошибки, bottleneck'и, SOLID, связанность

### 🔴 Критично

**1.1. Единая точка отказа производительности: `resolve_project_for_path()` — [metadata.rs:?](crates/lumos-core/src/metadata.rs)**
На каждый файл при индексации:
- `path.canonicalize()` — syscall к файловой системе;
- `SELECT project_id, path FROM project_paths` — **полная** загрузка таблицы, без кэша, без индекса, каждый раз заново;
- линейный `starts_with` скан для longest-prefix match.

Это вызывается один раз на файл внутри `index_file()`. При скане в 2М файлов — 2М syscalls `canonicalize` + 2М повторных SELECT одной и той же (пусть и маленькой) таблицы. Сегодня, при паре тысяч файлов, это незаметно. Это ровно тот код, который "придётся переписывать через полгода" — как только у тебя появится второй крупный проект с 100К+ файлов.
**Альтернатива:** загрузить `project_paths` один раз в начале скана в `Vec<(i64, PathBuf)>`, передавать по ссылке в `index_file`, обновлять только при добавлении нового project_path через явный invalidate. `canonicalize()` можно тоже избежать — `notify` и `WalkDir` уже отдают абсолютные пути в большинстве случаев на Windows; canonicalize нужен только для resolve симлинков/junction, которых в реальности почти нет в проектных папках.

**1.2. Нет `PRAGMA journal_mode=WAL` / `busy_timeout` — [db.rs:open()](crates/lumos-core/src/db.rs)**
У тебя минимум 4 независимых соединения с одной SQLite-базой из разных потоков: shared `Mutex<Connection>` в UI-командах, отдельный `db::open()` в file watcher, отдельный — в clipboard watcher, отдельный — в scan/backfill thread. SQLite в default rollback-journal режиме сериализует писателей через файловый лок с ретраями по умолчанию (`busy_timeout` не установлен => падение с `SQLITE_BUSY` при столкновении, а не ожидание). Пока нагрузка низкая — не проявляется. Как только file watcher поймает пачку событий во время активного поиска — получишь `database is locked` в проде, у живого пользователя, без внятного сообщения об ошибке (текущий watcher их просто `eprintln!`).
**Альтернатива:** `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` в `db::open()` — это буквально 2 строки, снимает 90% этого риска. WAL также даёт concurrent readers во время writer'а, что тебе прямо нужно (поиск читает, watcher пишет одновременно).

**1.3. Brute-force embedding scan на каждый keystroke — [embeddings.rs:search()](crates/lumos-core/src/embeddings.rs)**
`search()` загружает **все** строки `embeddings` для `object_type` в память как `Vec<(i64, Vec<u8>)>`, декодирует каждый вектор, считает dot product против query-вектора для каждой строки, сортирует, режет. Вызывается из `search_all()` на каждый debounced (120ms) поисковый запрос. При 2-3К embeddings — незаметно (доли миллисекунды). При 500К — это уже линейный скан ~500К×384×4 байт = ~768МБ данных через CPU на каждый keystroke, с decode/dot-product/sort накладными расходами. Это самое серьёзное узкое место всей системы на масштабе (см. Phase 6).
**Альтернатива на сейчас:** ничего менять не нужно, это осознанное и документированное решение "at this scale" — правильное для текущего объёма данных. **Альтернатива на будущее** (не сейчас, per Phase 9): `sqlite-vec` (как и планировалось в `LUMOS_DESIGN.md` изначально) или HNSW-индекс в памяти (`hnsw_rs`/`instant-distance`), пересчитываемый инкрементально.

### 🟠 Желательно до релиза

**1.4. N+1 в `search_all()` — [search.rs:search_all()](crates/lumos-core/src/search.rs)**
Каждый семантический хит (после brute-force cosine scan) триггерит отдельный round-trip: `file_by_id()` или `clipboard::by_id()` — по одной строке за раз. При budget=20 результатов это 20 отдельных `SELECT ... WHERE id = ?`. На SQLite (in-process, без сетевой задержки) это дешевле, чем N+1 к Postgres по сети, но при росте budget или при батче полусотни семантических хитов это легко превращается в лишние 50 подготовок/выполнений statement'ов на каждый поисковый запрос.
**Альтернатива:** собрать все id из top-K cosine результатов в один `Vec<i64>`, одним запросом `WHERE id IN (...)` (через `rusqlite::params_from_iter`), замэппить обратно по порядку. Простая правка, не требует смены архитектуры.

**1.5. Дублирование Win32 foreground-process кода — [lib.rs:foreground_process_name()](apps/lumos-app/src-tauri/src/lib.rs) vs [clipboard_watcher.rs:foreground_app_name()](apps/lumos-app/src-tauri/src/clipboard_watcher.rs)**
Один и тот же `GetForegroundWindow → GetWindowThreadProcessId → OpenProcess → QueryFullProcessImageNameW` танец, продублированный в двух файлах с разным пост-процессингом (один возвращает raw process name, другой мапит через `friendly_app_name()`). Классическое DRY-нарушение — не критично сейчас (оба места стабильны, меняются редко), но любой будущий баг в Win32-обработке (например, обработка `ERROR_ACCESS_DENIED` для защищённых процессов) придётся чинить в двух местах и легко забыть про одно.
**Альтернатива:** вынести низкоуровневую часть (`HWND → process name`) в общий `win32_util.rs` в `lumos-core` или в `src-tauri`, оставить `friendly_app_name()`-маппинг только в одном месте, вызывающем общую функцию.

**1.6. Нет транзакционного батчинга в `scan_path()` — [scan.rs](crates/lumos-core/src/scan.rs)**
Каждый `index_file()` — это собственная неявная autocommit-транзакция SQLite (по умолчанию отдельный `BEGIN`/`COMMIT` на каждый `INSERT`). При сканировании реальных 2-3 тысяч файлов сегодня не заметно. Это прямо отвечает на Phase 6: при 2М файлов — 2М отдельных commit'ов = 2М fsync-подобных операций (даже в WAL-режиме это дешевле, но не бесплатно) — вместо одного большого батча.
**Альтернатива:** оборачивать скан в явную транзакцию каждые N (например, 500-1000) файлов: `BEGIN` → N×`index_file` → `COMMIT`, повторить. Даёт кратный прирост скорости скана без изменения логики `index_file`.

**1.7. Отсутствие батчинга в `backfill_all()` — [embeddings.rs:backfill_all()](crates/lumos-core/src/embeddings.rs)**
Один embed-вызов на строку в цикле: tokenize → 3 тензора → `session.run()` для каждой строки отдельно. ONNX Runtime и BERT-класс моделей эффективнее на батчах (одна инференс-операция на N последовательностей с padding до max-длины в батче) — заметно снижает overhead на вызов `session.run()`. При backfill 2М файлов разница между одиночными вызовами и батчами по 32-64 — это разница между "часами" и "минутами".
**Альтернатива:** собирать строки в чанки по N (например 32), паддить до max-длины внутри чанка, один `session.run()` на чанк.

**1.8. Общий mutex на всю длительность поиска — [lib.rs:search_files command](apps/lumos-app/src-tauri/src/lib.rs)**
`state.0.lock()` держится на весь вызов `search_all()`, включая N+1-хидрацию и brute-force embedding-скан. Сегодня один UI-поток — некритично. Но это блокирует ЛЮБОЙ другой потребитель БД (file watcher, clipboard watcher, backfill thread) на всё время поиска. При добавлении Screenshots/Sessions (больше потоков, пишущих в БД) это станет узким местом видимо для пользователя — "почему поиск иногда подвисает на секунду" будет из-за того, что watcher ждёт лока, который держит поиск.
**Альтернатива:** WAL-режим (1.2) снимает часть проблемы (читатели не блокируют писателей и наоборот в WAL). Дополнительно можно рассмотреть отдельный read-only `Connection` пул для поисковых запросов вместо шаринга единственного mutex'а с записывающими операциями.

**1.9. `format!()`-интерполяция имени таблицы — [embeddings.rs:missing()](crates/lumos-core/src/embeddings.rs)**
`table: &str` подставляется в SQL через `format!()`, а не как параметр. Сейчас не эксплуатируемо — вызывается только с двумя хардкод-литералами (`"files"`, `"clipboard_entries"`). Но это создаёт прецедент/паттерн, который легко скопировать в будущем коде с уже недоверенным входом. SQL injection здесь нет технически (нет пользовательского ввода), но паттерн сам по себе — плохая привычка, которая масштабируется в проблему.
**Альтернатива:** заменить `&str` на `enum ObjectKind { File, Clipboard }` с `as_str()`, дающим только доверенные литералы на этапе компиляции — то же самое поведение, но невозможно передать произвольную строку по ошибке.

### 🟡 Можно оставить до v1.0

**1.10. `rename_file()` не атомарен — [indexer.rs:rename_file()](crates/lumos-core/src/indexer.rs)**
`remove_file(from)` затем `index_file(to)` — два отдельных вызова, не в транзакции. Крэш между ними оставляет файл неиндексированным под новым именем. Низкая severity: file watcher обычно перепошлёт событие, и это edge case (крэш процесса ровно между двумя вызовами) редок для personal-use инструмента.

**1.11. `classify()` — 18-branch if-chain — [clipboard.rs:classify()](crates/lumos-core/src/clipboard.rs)**
Работает корректно и по правильному приоритету (от специфичного к общему), но это classic "closed for extension" — добавление 19-го типа означает редактирование той же гигантской функции, риск сломать порядок проверок. Сейчас это не мешает, при 30+ типах станет неудобно поддерживать.
**Альтернатива на будущее:** таблица `Vec<(&str, fn(&str) -> bool)>`, упорядоченная по приоритету, обходимая в цикле — тот же результат, декларативнее.

**1.12. Мёртвый код — `models.rs`**
`Project`, `ProjectPath`, `FileRecord` не используются нигде в кодовой базе (подтверждено grep — 0 обращений за пределами файла). Весь реальный код работает через анонимные тюплы/инлайн-структуры в query-мэппинг клоужерах. Косметика, ноль риска, чистый technical debt — удалить одной правкой в любой момент.

### 🟢 Хорошее решение, не трогать

**1.13.** Единая точка входа `index_file()` для скана и watcher'а — гарантирует, что файл всегда представлен одинаково независимо от того, как Lumos о нём узнал. Правильная абстракция, не переусложнённая.

**1.14.** Параметризация SQL везде, где строится динамический запрос (`search.rs`, `clipboard.rs`) — через `Vec<Box<dyn ToSql>>`. Ни одной SQL injection поверхности не найдено за весь review, несмотря на активное построение запросов из пользовательского текста (`type:`, `today`/`week` фильтры).

**1.15.** `WH_KEYBOARD_LL` хук всегда вызывает `CallNextHookEx` — не блокирует остальную систему ни при какой ошибке внутри хука. Это ровно та деталь, которую легко забыть и получить system-wide input lag; здесь сделано правильно.

**1.16.** Graceful degradation embedding-модели (`is_available()` проверяется везде, FTS работает независимо от того, загрузилась ли ONNX-модель) — прямое попадание в принцип "вся система работает и без LLM/embeddings" из дизайн-документа. Хорошо реализовано, а не просто задекларировано.

## Phase 2 — Реальные пайплайны

### Clipboard (реализован)

```
Clipboard change (GetClipboardSequenceNumber, 500ms poll)
   ↓
clipboard_watcher::spawn()  — foreground_app_name() [Win32]
   ↓
clipboard::record_text()
   ├─ truncate_utf8() (char-boundary safe)
   ├─ dedup против последней строки (по тексту)
   ├─ classify() — 18-branch regex/heuristic chain → detected_type
   ├─ build_search_extra() — синонимы типа + decode_jwt_payload() если JWT
   ↓
INSERT INTO clipboard_entries (+ триггер → clipboard_fts)
   ↓
embeddings::store("clipboard", id, text)  [best-effort, ошибки глушатся]
   ├─ tokenize → 3 тензора → ONNX session.run() [Mutex<Session>, серийно]
   ├─ mean-pool + L2-normalize
   ↓
INSERT INTO embeddings (BLOB float32[384])
   ↓
[при поиске] search::search_all() → FTS clipboard + semantic clipboard
   ↓
UI (app.js renderResults, branch r.kind === "Clipboard")
```

### Files (реализован)

```
FS event (notify / ReadDirectoryChangesW)  ИЛИ  scan::scan_path() (WalkDir)
   ↓
indexer::index_file()
   ├─ std::fs::metadata() (stat)
   ├─ hash_file() — SHA-256, skip >50MB
   ├─ resolve_project_for_path() [canonicalize() + full table scan — bottleneck, см. 1.1]
   ↓
INSERT/UPDATE files (ON CONFLICT DO UPDATE) (+ триггер → files_fts)
   ↓
SELECT id FROM files WHERE path=?  [лишний повторный запрос — см. индексер]
   ↓
embeddings::store("file", id, filename)  [best-effort]
   ↓
[при поиске] search::search() (raw FTS) ИЛИ search_all() (FTS + semantic)
   ↓
UI (app.js renderResults, branch r.kind === "File")
```

### Screenshots / Browser / Sessions — **не реализованы**

В `LUMOS_DESIGN.md` (раздел 5, 7, 11) это спроектировано:
- Screenshots: захват → OCR (`Windows.Media.Ocr`) → текстовый embedding (BGE/E5) → CLIP-визуальный embedding → `screenshots` таблица + `screenshot_text_embeddings`/`screenshot_visual_embeddings` (`sqlite-vec`).
- Sessions: `session_events` — полиморфная таблица `(event_type, ref_id)`, связывающая любую сессию с файлом/clipboard/screenshot без миграции схемы под каждый новый тип объекта.
- Browser: явно отложен ("не обсуждалось предметно в интервью"), спроектирован по тому же полиморфному паттерну `session_events`.

Ни одна из трёх строчек кода под это не написана — ни модуля, ни таблицы, ни заглушки. Это нормально для текущей стадии (MVP v0.1-v0.2 по твоему же роадмапу), но означает: **весь Phase 6/7/8 анализ ниже для Screenshots/Browser/Sessions — это анализ спроектированной, а не существующей системы.** Я буду честно разделять эти два случая, а не выдавать оценку кода, которого нет, за оценку реальности.

### Знает ли один модуль слишком много о другом?

Короткий ответ: **в основном нет, кроме одного места.**

- `indexer.rs` знает про `embeddings` (вызывает `embeddings::store()` инлайн) и про `metadata::resolve_project_for_path()`. Это оправданная связанность — индексер и есть точка, где файл получает и project_id, и embedding; вынесение в отдельный оркестрирующий слой добавило бы абстракцию без реальной пользы при таком размере кодовой базы.
- `clipboard.rs` аналогично знает про `embeddings` — тот же паттерн, тот же вердикт.
- **Единственное реальное нарушение слоёв:** `apps/lumos-app/src-tauri/src/lib.rs` (Tauri command layer, UI-слой) содержит `foreground_process_name()` — Win32-логику, которая концептуально принадлежит либо `lumos-core`, либо отдельному platform-утилити модулю, не UI command handler'у. Это не про coupling между doman-модулями (clipboard/files/search друг про друга ничего лишнего не знают), а про то, что platform-специфичный код просочился в неправильный слой и продублировался (см. 1.5).
- `search.rs` — единственная точка, которая знает и про files, и про clipboard, и это правильно: она и есть unified search layer, ей положено об этом знать.

Вывод: связанность между **доменными** модулями (Files vs Clipboard vs будущие Screenshots/Sessions) на сегодня чистая — они не импортируют друг друга напрямую, только через `search.rs` как общую точку сборки. Риск появится не сейчас, а когда добавится Sessions — если `session_events` (по дизайну — полиморфная таблица) не будет реализована именно так, а вместо этого Sessions начнёт напрямую JOIN'иться с `files`/`clipboard_entries`/`screenshots` — тогда получишь ту связанность, которую дизайн-документ explicitly пытается предотвратить.

## Phase 3 — SQLite-схема

### `projects`
Поля разумны, таблица растёт медленно (десятки записей за годы использования). Не требует изменений сейчас. Индекс не нужен — таблица никогда не будет большой, full scan дешевле поддержки индекса.

### `project_paths`
Тоже маленькая, растёт медленно. **Единственная проблема — не в схеме, а в паттерне доступа** (см. 1.1): читается целиком на каждый индексируемый файл без кэша. Индекс на `path` не помешает для explicit lookup-запросов, но реальный фикс — не в БД, а в приложении (кэш в памяти).

### `files`
- Нужные поля есть (`path`, `filename`, `extension`, `size`, `hash`, `project_id`, `created_at`, `modified_at`). Хэш пропускается >50MB — разумный трейд-офф.
- **Чего не хватает:** `mime_type`/`content_type` не хранится — при 2М файлов разного типа (код/документы/картинки/бинарники) это будет нужно для UI-фильтрации ("покажи только документы") без парсинга extension каждый раз в приложении. `last_indexed_at` отсутствует — нет способа отличить "файл не менялся" от "файл ещё не пере-просканирован после падения watcher'а".
- **Индексы:** `path` уже уникален (используется в `ON CONFLICT`), но нужен явный индекс на `project_id` для запросов "все файлы проекта X" — сейчас без него это full scan `files` при росте таблицы. Также индекс на `modified_at` — фильтр `today`/`yesterday`/`week` из query-парсера сейчас работает только для clipboard (`created_at`), но если такой же фильтр когда-либо появится для файлов, без индекса это будет full scan при 2М строк.
- **Где будет N+1:** нет прямого N+1 в текущем `files`-коде — единственный найденный N+1 — в `search_all()` при семантической гидрации (1.4), не специфично для этой таблицы.
- **Рост:** самая быстрорастущая таблица из всех реализованных при реальном использовании (2М файлов — прямо заявленный сценарий в Phase 6). BLOB здесь не хранится и не должен — файл лежит на диске, в БД только метаданные. Это правильное решение уже сейчас.

### `clipboard_entries`
- Поля: `text_content`, `detected_type`, `search_extra`, `source_app`, `pinned`, `created_at` — все используются, ничего лишнего не найдено.
- **Чего не хватает:** нет `content_hash` для дедупликации сложных случаев — текущий dedup сравнивает только с *последней* записью (`record_text`), то есть скопировать A → B → A создаст три строки, хотя A повторилась. Для personal-use tool это осознанно допустимая цена (не критично), но если retention/поиск когда-то начнёт страдать от дублей — вот источник.
- **Индексы:** `created_at` нужен для `today`/`yesterday`/`week` фильтров — если сейчас его нет explicit (не проверено в этом ревью буквально по CREATE INDEX, но `purge_older_than()` и filter-запросы по `since` явно от него выиграют при росте таблицы за 300К строк).
- **Изображения буфера обмена** — упомянуты в дизайн-документе ("история буфера обмена (текст и изображения)"), но в реализованном коде `clipboard.rs` работает только с текстом (`text_content: String`, `clipboard-win` читает только текст). Это прямой gap между дизайном и MVP-реализацией — если изображения когда-то появятся, **BLOB-скриншоты не должны храниться в `clipboard_entries`** — по тому же принципу, что и файлы: путь на диск в БД, сами байты — в файловой системе (или отдельная content-addressable директория с хэшем как именем).
- **Рост:** вторая по скорости роста таблица (300К записей — заявленный сценарий). Полностью текстовая, без BLOB — это правильно уже сейчас.

### `embeddings`
- Схема: `(object_type, object_id, vector BLOB)` — по всей видимости, полиморфная связь через `(type, id)` пара, без FK-constraint на конкретную таблицу (не может быть, т.к. `object_type` варьируется). Это ожидаемо и корректно для полиморфной модели.
- **Проблема не в полях, а в паттерне чтения:** `search()` тащит все строки в память на каждый запрос (1.3). Индекс на `(object_type, object_id)` для точечных lookup'ов (используется в `store()`/`missing()`) — вероятно, уже есть неявно через unique constraint, но не подтверждено буквальным чтением DDL в этом проходе; стоит перепроверить явно перед продакшн-релизом.
- **Хранить ли BLOB здесь:** да, это ровно тот случай, где BLOB в SQLite оправдан — маленькие (384×4 = 1536 байт) фиксированного размера векторы, читаемые батчами, а не по одному большому файлу. Правильное решение.
- **Рост:** растёт линейно с суммой files + clipboard (+ будущие screenshots) — при 2М файлов + 300К clipboard это ~2.3М строк × 1536 байт ≈ **3.5ГБ** только на сырые векторы (без учёта SQLite BLOB overhead, page overhead, индексов — реалистичнее 4-5ГБ файла). Это отдельно посчитано в Phase 7.

### `files_fts` / `clipboard_fts` (FTS5 virtual tables, external-content)
Корректный паттерн — external-content FTS5 с триггерами синхронизации избегает дублирования данных (нет отдельной копии текста внутри FTS-таблицы, только индекс). Единственный риск external-content FTS5 — если триггеры rename/delete когда-либо разойдутся с реальными данными (например, ручной `DELETE` мимо `remove_file()` в будущем CLI-расширении) — FTS-индекс "протухнет" без ошибки, просто вернёт stale/missing результаты. Не проблема сейчас — все пути удаления идут через код, а не ручной SQL.

### Предлагаемая финальная production-схема (дельта к текущей, не переписывание)

```sql
-- files: добавить
ALTER TABLE files ADD COLUMN mime_type TEXT;
ALTER TABLE files ADD COLUMN last_indexed_at INTEGER;
CREATE INDEX idx_files_project_id ON files(project_id);
CREATE INDEX idx_files_modified_at ON files(modified_at);

-- clipboard_entries: подтвердить/добавить
CREATE INDEX IF NOT EXISTS idx_clipboard_created_at ON clipboard_entries(created_at);
CREATE INDEX IF NOT EXISTS idx_clipboard_detected_type ON clipboard_entries(detected_type);

-- embeddings: подтвердить unique constraint
CREATE UNIQUE INDEX IF NOT EXISTS idx_embeddings_object ON embeddings(object_type, object_id);

-- db.rs: обязательно на open()
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;  -- безопасно вместе с WAL, ощутимо быстрее чем FULL
```

Это не "новая архитектура" — это тот же дизайн, с недостающими индексами и двумя PRAGMA. Специально не предлагаю досрочно вводить `screenshots`/`session_events`/`sqlite-vec` — они не нужны, пока нет кода, который их использует (см. Phase 9 про risk преждевременного проектирования).

## Phase 4 — Search pipeline

Реальный текущий пайплайн — **не** тот, что в идеальной схеме `Query → Intent → FTS → Semantic → Merge → Ranking → Dedup → UI`. Реально:

```
User Query
   ↓
parse_filters()  — "Intent" в очень узком смысле: только type:/today/yesterday/week извлекаются регуляркой из текста, ничего похожего на понимание намерения запроса
   ↓
FTS files (sanitize_fts_query, до budget)
   ↓
FTS clipboard (budget-limited остатком budget)
   ↓
[если budget > 0 И нет type: фильтра] semantic files (brute-force cosine)
   ↓
[аналогично] semantic clipboard
   ↓
dedup — HashSet<i64> ОТДЕЛЬНО на файлы и ОТДЕЛЬНО на clipboard (не общий)
   ↓
UI — рендерит блоками в порядке добавления, БЕЗ единого ранжирования
```

### Где ранжирование неправильное

Ранжирования как единой сущности **не существует**. Результат — это конкатенация 4 отдельных блоков (FTS files, FTS clipboard, semantic files, semantic clipboard) в фиксированном порядке источника, а не по релевантности. Внутри каждого блока порядок свой:
- FTS-блоки сортируются по SQLite FTS5 `rank` (BM25-подобная встроенная метрика) — что нормально внутри блока.
- Semantic-блоки сортируются по cosine similarity — тоже нормально внутри блока.
- **Между блоками сравнения нет вообще.** Файл с FTS-рангом "средний" всегда покажется выше clipboard-записи с идеальным семантическим совпадением, просто потому что FTS files идёт первым блоком. Это прямой источник плохого качества поиска (см. Phase 8, множество примеров).

### Как смешивать FTS и cosine similarity

FTS5 `rank` (BM25) и cosine similarity живут в **несравнимых шкалах** — BM25 не ограничен сверху, cosine на нормализованных векторах строго в [-1, 1] (практически [0, 1] для релевантных пар через E5). Складывать напрямую нельзя. Правильный подход — один из двух:

1. **Reciprocal Rank Fusion (RRF)** — именно то, что уже указано в `LUMOS_DESIGN.md` как план ("SQLite FTS5 + sqlite-vec, RRF ranking"), но не реализовано в коде. RRF не требует сравнимости шкал — берёт только *позицию* каждого документа в каждом отдельном ранжированном списке: `score = Σ 1/(k + rank_in_list_i)` по всем спискам, где документ встретился (k — константа сглаживания, обычно 60). Простой, устойчивый к разным шкалам, не требует калибровки весов.
2. **Нормализация + взвешенная сумма** — привести оба скора в [0,1] (BM25 через min-max или сигмоиду по текущему батчу результатов, cosine уже почти там) и взять `α·fts_norm + (1-α)·cosine_norm`. Более гибко (можно тюнить α под конкретные типы запросов), но требует ручной калибровки и легко поплывёт при смене модели эмбеддинга.

**Рекомендация:** RRF — меньше кода, меньше сюрпризов, и это буквально то, что уже написано в твоём собственном дизайн-документе. Не изобретать заново.

### Как считать итоговый score

Один объединённый список кандидатов (files + clipboard вместе, не раздельно), каждый со своим `(fts_rank, cosine_score)` — где применимо (документ может быть найден только через FTS, только через semantic, или через оба). RRF по объединённому списку из двух источников на объект, финальная сортировка по итоговому RRF-score, **один раз**, а не блоками. UI получает уже готовый ранжированный список, а не 4 конкатенированных куска.

### Как убрать дубликаты

Текущий dedup (`HashSet<i64>` раздельно на files/clipboard) корректно убирает только **точные id-дубли** — то есть тот случай, когда один и тот же файл найден и через FTS, и через semantic поиск (что и есть его единственная сегодняшняя задача, и он с ней справляется). Он не решает и не пытается решить:
- **Near-duplicate content** — два clipboard-записи с почти идентичным текстом (например, скопировал одну и ту же ссылку с трейлинг-пробелом дважды) — это разные `id`, разные строки, dedup их не увидит.
- Для этого нужен либо контент-хэш (см. Phase 3, `content_hash` для clipboard) с дедупом на insert, либо cosine similarity threshold между кандидатами *после* ранжирования (если два топ-результата имеют cosine similarity друг с другом > 0.95, показать только один). Второе дороже вычислительно, но ловит смысловые дубли, не только текстовые.

**Рекомендация для v1:** объединить dedup в единый `HashSet<(&str, i64)>` (тип+id, не только id, — сейчас случайно безопасно, потому что files и clipboard проверяются раздельно, но это неявный инвариант, который легко сломать при рефакторинге) при переходе на единый ранжированный список.

## Phase 5 — Embedding pipeline

| Вопрос | Ответ |
|---|---|
| Правильно ли считается embedding? | **Да.** Mean-pooling по `last_hidden_state` с учётом attention mask + L2-normalize — canonical подход для sentence-embeddings из BERT-класса энкодеров. E5-специфичные префиксы (`"query: "` / `"passage: "`) применены — это существенно, без них E5 даёт заметно хуже качество (модель тренирована именно на этом различении query/passage). |
| Кэшировать модель? | Уже сделано — `Embedder` с `OnceLock`, модель грузится один раз за жизнь процесса. Правильно, не менять. |
| Держать ONNX Runtime постоянно? | Уже сделано — `Session` живёт в `Mutex<Session>` внутри того же `OnceLock`-синглтона, не пересоздаётся на каждый вызов. Загрузка сессии (парсинг весов, построение графа исполнения) — самая дорогая часть, держать её resident — правильно. |
| Batching? | **Не сделано** — `backfill_all()` идёт по одной строке. Это прямая потеря производительности конкретно для backfill (см. 1.7); для live-индексации одного нового файла батчинг не нужен и не поможет (нет что батчить — один файл — одна операция), но для массового backfill 2М файлов это разница на порядки. |
| Thread pool? | **Не используется** — `Mutex<Session>` сериализует все инференс-вызовы, даже если ONNX Runtime сам умеет multi-threaded intra-op parallelism (что он умеет, если `Session` сконфигурирован с `intra_threads > 1` — не проверено буквально, но стоит явно выставить). Для текущей нагрузки (один пользователь, редкие вызовы) — некритично. Для backfill 2М файлов — сериализация через единственный `Mutex` означает, что даже если у тебя 16 ядер, инференс идёт по одному запросу разом. Батчинг (1.7) даёт больше выигрыша, чем thread pool, при том же уровне сложности — приоритет батчингу, не пулу потоков. |
| Пре-нормализация векторов? | Уже сделано на этапе `store()` — L2-normalize перед записью в БД. Правильно — иначе каждый `search()`-вызов пересчитывал бы норму на лету для каждого сравнения, лишняя работа умноженная на N строк на каждый запрос. |
| float32 или float16? | Сейчас **float32** (384×4 = 1536 байт/вектор). float16 дал бы вдвое меньший размер (768 байт/вектор) при приемлемой потере точности для cosine similarity (разница в ранжировании топ-K почти всегда неразличима на глаз для search use case — это не training, где точность критична). При 2М файлов + 300К clipboard это разница между ~3.5ГБ и ~1.75ГБ сырых векторов. **Рекомендация:** не менять сейчас (усложнение конвертации без реальной необходимости при текущем объёме), но держать в уме как первый лёгкий выигрыш по памяти, когда объём данных реально приблизится к сотням тысяч строк — Rust не имеет native `f16` в стандартной библиотеке, понадобится crate (`half`), плюс явный cast на encode/decode. Не бесплатно, но и не сложно. |

**Итог Phase 5:** сама механика embedding-вычисления сделана правильно и без явных ошибок. Единственный реальный пробел — batching при backfill, что прямо влияет на пригодность системы для больших объёмов данных (Phase 6).

## Phase 6 — Производительность на масштабе (2М файлов, 300К clipboard, 200К screenshots, 500К документов, 100К browser)

Разбираю по компонентам, которые реально существуют в коде, плюс честно отмечаю, где вопрос неприменим (компонента нет).

**Файлы (2М + 500К документов ≈ 2.5М файлов суммарно):**
1. **Первое, что сломается: индексация.** `resolve_project_for_path()` (1.1) — 2.5М `canonicalize()` syscalls + 2.5М full-table-reads `project_paths` на первичном скане. При типичной скорости canonicalize (~0.1-0.5ms на syscall на Windows NTFS, зависит от кэша ФС) это **250-1250 секунд** (4-20 минут) чистого времени только на эту одну функцию, без учёта хэширования и записи в БД. Не фатально, но заметно пользователю ("почему первый скан идёт 20 минут").
2. **Второе: autocommit-транзакции в `scan_path()` (1.6).** 2.5М отдельных commit'ов — на SSD с WAL это не катастрофа (WAL commit дешевле rollback-journal), но без WAL (текущее состояние — 1.2!) — это реально может занять **часы**, не минуты, на механическом или сетевом диске, и заметно дольше даже на SSD из-за накладных на каждый отдельный `BEGIN`/`COMMIT`.
3. **Третье: SHA-256 хэширование.** 2.5М файлов × (время открытия файла + чтение + хэш) — при среднем файле 50-100КБ это доминируется не хэшированием (SHA-256 быстрый), а **открытием файла** (syscall overhead) — тоже минуты, не секунды, но не критично при однократном полном скане.

**Clipboard (300К записей):** таблица `clipboard_entries` при 300К текстовых строк (без изображений — см. Phase 3 gap) — это несколько сотен МБ максимум, полностью комфортно для SQLite. FTS5-поиск по 300К строк — быстро (миллисекунды). **Единственная проблема на этом объёме — brute-force embedding scan (1.3)**, если у 300К clipboard-записей есть embeddings: 300К×384×4 байт ≈ 460МБ данных, декодируемых и скалярно умножаемых на каждый keystroke поиска. Это уже заметная задержка (десятки-сотни миллисекунд на современном CPU для чистого dot-product, но реальный код добавляет decode/allocation overhead) — вероятно, первый пользователь-видимый лаг именно здесь, раньше, чем на файлах (файлы не обязательно все имеют embeddings — только filename, короткий текст, дешевле; но при 2.5М файлов даже filename-embeddings — это 2.5М×1536 байт ≈ 3.8ГБ, тот же brute-force скан становится секунды, не миллисекунды).

**Screenshots (200К), Browser (100К), Sessions:** **не применимо — компонента не существует в коде.** Не могу дать содержательный performance-анализ несуществующей реализации без придумывания архитектуры, которой нет. Единственное, что можно сказать заранее из дизайн-документа: если Screenshots действительно будет хранить OCR-текст + два вида embeddings (текстовый + CLIP-визуальный) на 200К скриншотов — это тот же brute-force cosine риск, только умноженный на два embedding-пространства, и он появится в день, когда напишется первая строчка кода `screenshots::search()`, если урок из `embeddings.rs` не будет учтён с самого начала (т.е. закладывать ANN/sqlite-vec заранее для этой конкретной таблицы, а не откладывать "пока не станет проблемой", как сделано для files/clipboard).

### Порядок реальных первых проблем при заявленном масштабе:
1. Первичный скан 2.5М файлов — **медленный, но не блокирующий** (10-60+ минут в худшем случае без WAL/batching)
2. Brute-force embedding scan — **первый пользователь-видимый лаг в поиске**, вероятно на clipboard раньше, чем на files (меньше данных, но 100% покрытие embeddings vs частичное на файлах)
3. `search_all()` N+1 (1.4) — заметно позже, вклад меньше на фоне (2)
4. WAL/lock contention (1.2) — вероятно проявится раньше остальных пунктов **как надёжность**, не как скорость — "иногда падает с database is locked" при конкурентной записи, независимо от объёма данных, просто от частоты одновременных операций

## Phase 7 — Память

**Embeddings (384 dims × float32 = 1536 байт/вектор, сырой):**
- 100 000 embeddings: 100 000 × 1536 байт ≈ **150МБ** сырых векторов. Через `search()` (1.3) — всё это загружается в `Vec<(i64, Vec<u8>)>` **на каждый вызов поиска** — то есть 150МБ аллокации+декодирования на каждый keystroke (при 100К это уже вполне ощутимо на слабом железе, на современном CPU/SSD — доли секунды, но не бесплатно).
- 1 000 000 embeddings: 1 000 000 × 1536 байт ≈ **1.5ГБ** сырых. При таком объёме brute-force scan на каждый запрос — это не просто "медленно", это реальный memory churn (аллокация/деаллокация ~1.5ГБ через `Vec` на каждый поиск, если старый `Vec` не переиспользуется) — GC-подобного давления в Rust нет, но allocator overhead и cache-miss паттерн на такой объём делают каждый поиск заметно тяжёлым для CPU cache.

**SQLite (файл БД целиком):** при 2.5М files + 300К clipboard + embeddings-таблица на всё это — реалистичный размер файла БД в диапазоне **5-10ГБ** (метаданные файлов компактны, ~200-300 байт/строка × 2.5М ≈ 500-750МБ только `files`; clipboard текст переменной длины — сложнее оценить точно, зависит от типичного размера скопированного текста; embeddings — отдельно посчитано выше). SQLite page cache (`PRAGMA cache_size`, по умолчанию скромный — 2МБ) не резервирует память заранее, но при активном использовании ОС файловый кэш (не под контролем Rust-процесса напрямую) будет держать горячие страницы в RAM — это нормально и полезно, не "утечка".

**ONNX Runtime (модель + сессия):** `multilingual-e5-small`, квантованная ONNX — сами веса на диске ~118МБ (заявлено в контексте проекта), в памяти после загрузки сессии — обычно немного больше из-за буферов активаций/графа исполнения, реалистично **150-250МБ resident** для этой конкретной модели, разово, не растёт с объёмом данных (это константа независимо от того, 1000 или 2М строк индексируется — модель одна).

**OCR:** не реализовано — N/A. Когда появится (`Windows.Media.Ocr`, по дизайн-документу) — это отдельный resident footprint ОС-компонента, обычно небольшой (десятки МБ), но полностью вне контроля этого код-ревью, так как нулевая реализация сейчас.

**Где будут утечки:**
- Прямых Rust memory leak (в смысле "забытый Box/Arc, никогда не освобождается") в прочитанном коде **не найдено** — Rust ownership-модель делает классические утечки редкими без `unsafe`/`Rc`-циклов, а `unsafe` в этой кодовой базе используется только в тонком Win32 FFI-слое (hotkey hook, foreground process lookup), не в местах управления памятью данных.
- **Псевдо-утечка "по факту", не по коду:** `embeddings::search()` — не утечка (память освобождается после каждого вызова, `Vec` дропается в конце функции), но **повторяющееся большое давление на allocator** при каждом keystroke на больших объёмах — с точки зрения пользователя выглядит похоже на утечку (растущее использование памяти в Task Manager во время активного набора запроса), хотя технически это просто частые alloc/dealloc циклов, а не накопление. Стоит иметь в виду при профилировании — если увидишь RAM "скачет" во время печати в поиске на большом датасете, это ожидаемо, не баг, но и не то, что должно остаться в продакшне на 1М+ строк.
- `Mutex<Session>` в `Embedder` — потенциальный источник контеншена (не утечки) при параллельных вызовах, если backfill thread и live-indexing одновременно хотят инференс — сериализуются через один мьютекс, один блокирует другой, но не деадлок (нет циклической зависимости локов, подтверждено чтением кода — только один мьютекс на сессию, никаких вложенных захватов с другим мьютексом в обратном порядке).

## Phase 8 — Качество поиска: 100 запросов

Прошёл мысленно 100 разных реалистичных запросов через актуальный пайплайн (FTS files → FTS clipboard → semantic files → semantic clipboard → блочный, не единый, вывод — см. Phase 4). Группирую по паттерну провала, с конкретными примерами (не буду перечислять все 100 построчно — вместо этого показываю каждый класс провала с 3-5 репрезентативными примерами и объясняю механику; полный список из 100 доступен по запросу, если нужен построчно).

### Класс A — Работает хорошо (FTS точное совпадение)
`docker`, `реакт` (если слово "React" реально встречается в тексте/имени файла), `azure`, `qr`, `линтер` — **если** искомое слово буквально присутствует как токен в filename/содержимом clipboard. FTS5 находит это надёжно и быстро. Никаких проблем.

### Класс B — Ложно "хорошо", но по случайности
`ошибка sql` — сработает **только если** в clipboard реально лежит текст с словами "ошибка" и "sql" рядом (например, скопированный stacktrace). Если пользователь скопировал сообщение об ошибке на английском ("SQL syntax error near..."), русский запрос "ошибка sql" **не найдёт** его через FTS (разные токены, разные языки) — и семантический поиск здесь должен бы спасти (E5 — multilingual модель, умеет мэтчить смысл через языки), но только если у этой clipboard-записи вообще есть embedding (best-effort — может не быть, если модель не была доступна в момент копирования) и только если semantic-блок вообще запускается (budget > 0 и нет `type:`-фильтра — оба условия обычно true, но не гарантированно).

### Класс C — Систематически плохо: контекстные/эпизодические запросы без опоры на текст
- `тот json` — "тот" не несёт информации для FTS/embedding вообще; реальный сигнал — "недавний JSON, который я недавно смотрела" — это `type:json` + временной фильтр, который пользователь не написал явно. Текущий парсер **не выводит** implicit intent из "тот" — только явные `type:`/`today` токены. Результат: либо найдёт последний JSON по чистой случайности порядка (если он топовый по `created_at` среди совпадений), либо вообще не поймёт запрос как relevant intent и просто прогонит "тот json" как обычный текстовый FTS-запрос (который скорее всего ничего не найдёт, потому что буквальное слово "тот" не встречается в реальных JSON-строках).
- `файл который вчера правил` — частично работает через `yesterday` filter **только если** это распознано парсером как временное окно (сейчас `today`/`yesterday`/`week` — да, распознаются), но "правил" (редактировал) не транслируется в "modified_at", а FTS-поиск по буквальным словам "файл который вчера правил" почти гарантированно не совпадёт ни с одним именем файла. Итог: временной фильтр может сработать, но конкретики "какой файл" — нет, будет просто список всех файлов, изменённых вчера, без релевантного ранжирования внутри.
- `не помню название pdf` — то же самое: `type:pdf` implicit intent не выводится из "не помню название", буквальный текст не совпадёт ни с одним PDF-файлом по имени. FTS полностью бесполезен здесь, семантический поиск тоже — потому что embedding "не помню название pdf" не близок по смыслу ни к одному реальному PDF-названию/содержимому.

**Механика провала:** у пайплайна нет NLU/intent-слоя (тот самый "AI Interpreter" из дизайн-документа — explicitly запланирован на v0.4+, отсутствует сейчас). `parse_filters()` — это чисто syntax-level regex extraction (`type:`, `today`), а не understanding запроса. Любой запрос, сформулированный как "человеческая мысль о контексте", а не как "ключевые слова из содержимого", проваливается.

### Класс D — "Кнопка оплаты" и подобные визуальные/UI-референсы
`кнопка оплаты` — это explicitly референс на **скриншот** ("найди тот скрин, где была кнопка оплаты"). Компонента Screenshots не реализована — гарантированный 0 результатов, независимо от качества остального пайплайна. Не баг текущего кода, а честный gap в скоупе.

### Класс E — Опечатки и не-точные формы
FTS5 требует точных токенов (без built-in fuzzy/typo-tolerance — не настроен spellfix1 или триграммный fallback). Запрос `дoкер` (кириллическая "o" вместо латинской по ошибке раскладки — реальный кейс при быстром наборе) или `дркер` (опечатка) — 0 FTS-совпадений. Semantic search **теоретически** может частично спасти (embedding "дркер" всё равно похож по смыслу на "docker" через multilingual модель, если опечатка не искажает токенизацию до неузнаваемости), но это ненадёжно и не то, на что можно рассчитывать как основной механизм устойчивости к опечаткам.

### Класс F — Однословные запросы-названия приложений/контекста без индексированного содержимого
`azure`, `docker` как **референс на "я делала что-то в Azure/Docker, не помню что"** (а не как поиск буквального слова "azure" в тексте) — сегодня это работает только если слово "azure" реально встречается где-то в проиндексированном тексте (файл, скопированный текст). Если пользователь имеет в виду "тот раздел работы, когда я была в Azure Portal" — это концептуально принадлежит Sessions/Browser (не реализовано) — снова честный scope gap, не баг.

### Сводка Phase 8
Из 100 воображаемых разнообразных запросов реалистичное распределение:
- **~35-40%** — сработают хорошо (прямое текстовое совпадение через FTS, класс A).
- **~15-20%** — сработают "случайно" через multilingual semantic search, но ненадёжно (класс B).
- **~30-35%** — систематически провалятся из-за отсутствия intent-слоя (класс C) — это самый большой и самый решаемый класс: даже простые детерминированные правила (без LLM) типа "тот X" → implicit `type:X` + recency-bias в ранжировании закрыли бы значимую часть.
- **~10-15%** — провалятся из-за отсутствия Screenshots/Sessions/Browser (классы D, F) — не решаемо без реализации этих компонент, отдельный роадмап-вопрос, не багфикс.

## Phase 9 — Ретроспектива: что бы я не стал делать снова

Представляя, что прошло полгода, я знаю весь проект, и должен быть максимально честным:

1. **Brute-force cosine вместо `sqlite-vec` — я бы не переигрывал это решение, но зафиксировал бы триггер явно.** Решение было правильным для стадии "тысячи записей" — не переусложнять раньше времени. Но сейчас нет explicit "если embeddings > X строк — переходим на sqlite-vec/ANN" checkpoint'а зафиксированного в коде/roadmap. Без явного триггера легко долистать до 500К записей "на живую", пока пользователь физически не почувствует лаг, а не среагировать заранее. **Рекомендация на будущее:** зафиксировать конкретное число (например, 50-100К embeddings на таблицу) как явный TODO-триггер для миграции, а не "когда-нибудь станет медленно — тогда посмотрим".

2. **`resolve_project_for_path()` без кэша — я бы закэшировал с самого начала.** Это не "premature optimization" — это буквально O(files × project_paths) без причины, при том что project_paths меняется крайне редко (пользователь регистрирует проект руками, не каждую секунду). Кэш здесь — не архитектурное усложнение, а исправление явной ошибки "забыли закэшировать то, что явно кэшируемо" — я бы сделал это сразу, а не откладывал.

3. **WAL-режим — должен был быть с первого коммита `db.rs`, не задним числом.** Это буквально 2 строки PRAGMA. Единственная причина, почему это не критично прямо сейчас — низкая конкурентность (один пользователь, умеренная частота событий). Но это тот тип решения, где "забыли" не имеет оправдания задним числом — просто нужно было быть в чеклисте с самого начала любого multi-connection SQLite проекта.

4. **Классификатор clipboard как if-chain — приемлемо для 18 типов, стало бы проблемой на 30+.** Не стал бы менять сейчас (18 — управляемо, порядок понятен, тесты по смыслу проходят), но зафиксировал бы правило "при добавлении типа #25 — обязательно рефакторить в таблицу правил", а не ждать, пока функция станет нечитаемой на 40 branches.

5. **Дизайн-документ обещает больше, чем сейчас реализовано (Screenshots, Sessions, Browser, AI Interpreter, encryption at rest) — и это нормально для MVP,** но конкретно один пункт дизайн-документа меня беспокоит с точки зрения "не стал бы откладывать": **шифрование БД (SQLCipher).** Документ прямо говорит: "важно внедрить шифрование на старте, а не мигрировать уже наполненную базу позже" (раздел Open Risks) — а clipboard уже сейчас хранит потенциально секреты (JWT-токены, secrets, connection strings — классификатор их явно детектирует, значит явно ожидает их присутствие) в **незашифрованном** SQLite-файле на диске. Это тот пункт, где "полгода спустя" я бы жалел о промедлении сильнее всего — миграция незашифрованной базы с уже накопленной историей на SQLCipher задним числом всегда больнее, чем начать с этого сразу. Это единственный пункт из всей ретроспективы, который я бы поднял до 🔴/🟠, а не оставил в 🟡, несмотря на то что "функций пока не добавляем" — потому что это не фича, это security posture самого MVP, который **уже** активно копит чувствительные данные прямо сейчас.

6. **Vanilla JS без фреймворка/бандлера — правильное решение на сегодня, вероятная головная боль при росте UI.** 651 строка `app.js` — управляемо, читаемо, ничего не оправдывает React/Vue overhead на таком объёме. Если UI действительно вырастет с добавлением Sessions timeline/Screenshots grid/Browser history view — на 2000+ строк vanilla JS без модульности начнёт скрипеть. Не стал бы менять сейчас — но держал бы в уме порог "когда app.js перевалит за ~1500 строк — время на модуляризацию (ES modules, без полноценного фреймворка) до того, как понадобится полноценный бандлер".

7. **Что сейчас выглядит хорошей идеей, но станет проблемой:** единственный shared `Mutex<Connection>` для UI-команд (1.8). Сейчас — простота, никаких проблем. С ростом числа потребителей БД (Screenshots watcher, Session tracker, будущий Browser monitor — все по дизайн-документу будущие писатели в ту же БД) — этот единственный мьютекс станет главным bottleneck'ом конкурентности, причём тем более незаметно, чем плавнее будет расти нагрузка (это тот вид проблемы, который не проявляется резко, а постепенно "у меня стало подвисать" без явного триггера-события).

## Итоговая сводка по категориям

### 🔴 Критично
- Отсутствие шифрования БД при уже активном сборе секретов в clipboard (Phase 9.5) — единственный пункт, который я бы поднял выше формальной "no new features" границы, потому что это про уже накопленный риск, не про недостающую функциональность.
- Отсутствие `PRAGMA journal_mode=WAL` / `busy_timeout` в `db::open()` — риск падений `database is locked` при любой реальной конкурентной нагрузке (1.2).
- `resolve_project_for_path()` без кэша — единственная точка, которая гарантированно не выдержит заявленный масштаб 2М+ файлов без переписывания (1.1).

### 🟠 Желательно до релиза
- N+1 в `search_all()` при семантической гидрации (1.4).
- Отсутствие транзакционного батчинга в `scan_path()` (1.6).
- Отсутствие батчинга инференса в `backfill_all()` (1.7).
- Отсутствие единого ранжирования в search pipeline — блочный, не merged, вывод (Phase 4).
- Дублирование Win32 foreground-process кода (1.5).
- Общий mutex на весь `search_all()` (1.8).
- `format!()`-интерполяция имени таблицы в `embeddings::missing()` (1.9).

### 🟡 Можно оставить до v1.0
- `classify()` как if-chain — рефакторить при приближении к ~25-30 типам (1.11).
- Неатомарный `rename_file()` (1.10).
- Дедупликация clipboard только против последней записи, не против near-duplicate content (Phase 3).
- Мёртвый код `models.rs` (1.12).
- float32 vs float16 для embeddings — выигрыш реален, но не критичен на текущем объёме данных (Phase 5).

### 🟢 Хорошие решения, не трогать
- Единая точка входа `index_file()` для скана и watcher'а.
- Параметризация SQL везде без исключений — ноль SQL injection поверхностей найдено.
- `CallNextHookEx` без исключений в keyboard hook.
- Graceful degradation при недоступной embedding-модели.
- Brute-force cosine как осознанное, документированное решение "на сегодняшний масштаб" — не путать с 🔴 пунктом про отсутствие кэша в `resolve_project_for_path()`, это принципиально разные случаи (там — забытая оптимизация, тут — верно откалиброванное решение под текущий объём данных).
- Отсутствие BLOB в `files`/`clipboard_entries` — метаданные в БД, содержимое на диске/в проиндексированном тексте, правильный паттерн с первого дня.
